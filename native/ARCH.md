# Native synthesizers

## SoundFont engine

`synth.c` builds into `vendor/runtime/midi-synth.wasm` (`make wasm`). It wraps TinySoundFont (`tsf.h`, version 0.9, MIT, copied unchanged with its notice at its head) behind a small C ABI: `synth_buffer` and `synth_load` load a SoundFont, `synth_message` plays one MIDI channel message (FFh is a General MIDI reset), `synth_set_preset` selects any bank and program on a channel, `synth_render` renders up to 128 planar frames, `synth_voices` counts the sounding voices, and `synth_preset_*` list the presets.

The module knows nothing of time or byte streams. `src/engine.ts` dispatches complete messages between render calls, so each message acts at its own output frame. The General MIDI reset puts channel 10 on the drum kits of bank 128 and sets channel volume to 100, because TinySoundFont's own reset leaves volume at 127.

The build is standalone (`-sSTANDALONE_WASM`) with memory growth, so it has no JavaScript glue and one import. VERIFIED: over three interleaved rounds on an Apple M5 Max under Node 24, the medians of `-O2`, `-O3` and `-Os` for 32 notes over 20 s of audio lay within 1% of each other (172.7 to 174.4 ms), and `-O3 -msimd128` took 187.2 ms, 8% longer. The build uses `-O2`. VERIFIED: two builds with the same emcc gave identical bytes. A different Emscripten version can emit different bytes, which `scripts/integrity.mjs` then reports until `make wasm` records them.

## FM engine

`fm.cpp` builds into `vendor/runtime/fm-synth.wasm` (`make wasm`, `-O2 -msimd128`, 331,470 bytes). It wraps libADLMIDI 1.6.2's real-time API: `fm_init` sets the rate, the chips (1 to 8) and the embedded bank, `fm_set_bank` and `fm_load_bank` change the instruments (a WOPL file through `fm_buffer`), `fm_message` plays one channel message, `fm_sysex_buffer` and `fm_sysex` pass one SysEx message to libADLMIDI's `adl_rt_systemExclusive`, `fm_render` renders up to 128 planar frames, and `fm_voices`, `fm_chips` and `fm_bank_name` describe the state. Like the SoundFont module it knows nothing of time and imports only `emscripten_notify_memory_growth`.

FFh ends every voice and sends libADLMIDI an XG System On. `adl_rt_resetState` alone resets the controllers but keeps the synth mode that a GM System On or a GS reset selected, so that mode would outlive the host's own reset (stop, seek, an engine switch, a reset event); the XG System On restores the mode libADLMIDI starts in. VERIFIED: `scripts/fm-parity.mjs --full` rendered 86,400,000 frames of game files identical to the 0.3.0 module, so the change leaves the output of those files as it was.

`adlmidi/` is libADLMIDI (commit `ad001c83551779934bacd642fce801c51a5b7b4c`) trimmed to the files this build compiles: the MIDI sequencer and every chip emulator but Nuked OPL3 fast 1.8-fast.3 (commit `f44bacb1143cd78d36bacf69fbec8c60a125b3c9`) are left out. The changes to the copies:

- `src/adlmidi_opl3.cpp` knows only the Nuked fast chip; `src/structures/pl_list.tcc` aborts where it threw, since the build has no exceptions; `src/chips/opl_chip_base.h` makes the resampler's members protected.
- `src/chips/nuked_fast/nukedopl3_block.inc.c` is this project's block renderer, included at the end of `nukedopl3_fast.c`, and `src/chips/nuked_opl3_fast.cpp` calls it through `generate32`, then applies the resampler's own integer interpolation. `-DDEFUSS_OPL3_PER_SAMPLE` builds the unchanged per-sample path, against which `make wasm` checks every build (see [../ARCH.md](../ARCH.md)).
- `nukedopl3_fast.c` stops the build with `#error` under configurations the block renderer does not reproduce.

libADLMIDI's contribution rules (its `AGENTS.md`) refuse code generated by language models. The block renderer was written with one, so it stays in this project and is not offered upstream.

## Hardware profile cores

`profiles/` holds the eight native profiles' adapters and in-tree cores. `profiles/profile_pack.h` is their shared contract: the ABI 2 exports, the DSPK pack parser, and the SysEx framing and reset checks that every core applies the same way. [../HARDWARE_PROFILES.md](../HARDWARE_PROFILES.md) lists the exports, the pack roles and each core's limits; [../ARCH.md](../ARCH.md#hardware-profiles) explains why every core is its own reactor behind that contract.

Two builders make the modules:

- `scripts/build-vintage-wasm.py` compiles the in-tree C cores, `pci128.c` (ECW) and `gus.c` (GF1), with an LLVM clang for wasm32 against `profiles/freestanding/`, a minimal `string.h`, `stdlib.h` and runtime. These cores need no libc beyond that, so they build without an SDK and import nothing (`tests/vintage-wasm.test.ts` checks both).
- `scripts/build-native-profiles.py` fetches each upstream core at the commit its `LOCK` table pins, refuses a checkout that differs from it, and compiles it with Emscripten (`emcc`, `em++`, `emar`) using `-sSTANDALONE_WASM -sFILESYSTEM=0`, then rejects a module that imports anything outside the host's list or lacks an export (`check`). The upstream cores are C++ or need libc, which Emscripten's standalone mode supplies without JavaScript glue.

VERIFIED: two builds of each Emscripten core gave identical bytes (the CQM, Sound Canvas, MT-32 and AWE unit reports).

### CQM profile

`cqm.cpp` is the ABI 2 adapter: a libADLMIDI player on one chip, with libADLMIDI's embedded bank or a WOPL bank as its pack. `cqm_adlmidi.cpp` implements libADLMIDI's `NukedOPL3Fast` chip class with the Nuked CQM core of 86Box, and the build compiles it in place of `nuked_opl3_fast.cpp`, with no OPL3 core. The CQM takes the YMF262's register set (18 channels, 4-operator and rhythm modes, the C0 pan bits), so replacing the chip class lets libADLMIDI's driver, its 79 banks and its volume models drive the CQM unchanged; a driver of its own would duplicate libADLMIDI for one chip. The builder extracts `snd_cqm_nuked.c` up to `#define CQM_CLOCK`, since 86Box's ISA driver after that line needs the emulator's timers and CPU clock.

The chip runs at 49,716 Hz, the rate 86Box's driver passes to `CQM_Reset` since its commit f0f3c47209 "Fix CQM pitch", and libADLMIDI's native rate, so its resampler runs as for the OPL3. VERIFIED: A4 sounds at 439.24 Hz on the CQM and 439.22 Hz on the OPL3 (`tests/cqm.test.ts` asserts 440 Hz within 1%).

The output is not halved. 86Box halves both its Nuked OPL3 and its Nuked CQM driver output before the same Sound Blaster mixer; libADLMIDI halves neither chip, so taking `CQM_Generate`'s output unscaled keeps the two chips in 86Box's relation. VERIFIED: even so the CQM measures 7 to 8 dB quieter than the OPL3 for the same patches (the CQM unit's measurement).

A reset (FFh, or the GM, GM2, GS or XG reset SysEx) makes a new player on a new chip. VERIFIED: libADLMIDI's own reset (`adl_panic` with `adl_rt_resetState`) left a difference energy of 9.0 against a signal energy of 4.3 (the CQM unit's probe), while a new player matches a new instance bit for bit (`tests/cqm.test.ts`). `-msimd128` gave no gain (74 µs per block, 4 KB larger), so the CQM build leaves it off.

### Sound Canvas profiles

`roland_sc.c` runs SoundCarcass's SC-55 or SC-55mkII board (`MODEL_ID` 7 or 8): the original control program on its H8/532 interpreter and the GP sound chip at its own clock. It takes the place of SoundCarcass's `scemu.c`, whose model table links every board of the library; the XV, SH-2 and DSP cores behind it need SLJIT code generators without a wasm32 backend. VERIFIED: at the pinned submodule SLJIT's unsupported configuration stops with `#error` (the SC-55 unit report). The builder compiles the twelve files of `SC_SOURCES` from the pinned CMake lists, and a three-line header gives `core/jit.h` its type names without any SLJIT code.

The adapter checks each ROM image's size and CRC32 against the dump SoundCarcass's ROM finder names, boots the firmware in `profile_init`, feeds MIDI into the firmware's input at the cable's 31,250 baud with running status, and renders the DAC words. FFh sends a GS Reset, the reset the firmware takes from MIDI IN. The modules import nothing and run in a fixed 32 MiB memory.

### MT-32 profile

`roland_mt32.cpp` wraps libmt32emu's C++ API. The builder compiles Munt's pinned source lists with `em++` and archives them with `emar`, generating `config.h` from upstream's template, so no CMake is needed. ROMs are identified by Munt's own SHA-1 table; FFh plays the MT-32's All Parameters Reset (`7F 00 00`) as SysEx.

The adapter renders one frame per Munt call. Munt's TVP draws timer jitter from `rand()` partial by partial within each render call, so the size of the call changed the order of the draws and the output. VERIFIED: with one frame per call, partitions of 128, 64, 7 and 1 frames gave identical output, at 1.6 times the render time with 32 partials (0.073 to 0.116 ms per 128 frames, fake ROMs).

### AWE profiles

`awe.cpp` compiles AWE32Emu's pinned sources unmodified. They open the ROM and the banks by path, and the adapter's `fopen()` resolves three logical names to the pack's records with `fmemopen()`; a `__wasi_fd_read` that returns EBADF keeps `std::cin` from importing a read. The driver layer has no reset entry point, so a reset rebuilds the synthesizer from the same records. Upstream checks the Win95 pan glide once per `RenderBlock` call, so the adapter renders one frame per call for the longest glide, 255 steps of 227 frames, after a CC10. VERIFIED: before that change 128-frame and 1-frame calls differed in 34,670 samples; after it the tests find every driver family partition-invariant, and a shortened glide window fails them (the AWE unit report). The builder writes these modules only to `profile-assets/local-builds/` and only with `--local-awe`, because AWE32Emu's driver layer has no licence.

### ECW and GF1 cores

`pci128.c` parses an original ECLW waveset (bank and drum maps, instruments, layers, patches, sample headers and the signed 16-bit waveform) by Engelmann's ECW specification 1.5 and plays it at 22,050 Hz with up to 64 voices. Where the specification and ecw2sfz disagree with the wavesets' own data, the core follows the data; its header lists those decisions, and [../HARDWARE_PROFILES.md](../HARDWARE_PROFILES.md#sb-pci128) lists what they rest on.

`gus.c` reads GF1PATCH110 patches by the Gravis SDK 2.10 layout and plays them through `gf1_mixer.h`, an adaptation of QEMU's GUSEMU32 mixer that keeps its MIT notice. Where GUSEMU32 differs from the SDK (ramp speed, linear pan, loop restart), the mixer follows the SDK. The native rate is the SDK's table, floor(617,400 / voices).
